# リモートホスト

Hyla は、Linux の開発マシン、クラウドの VM、机の下の Mac mini、WSL ディストリビューションなど、ほかのマシンで動くセッションを、ローカルのセッションと同じウインドウに表示できます。同じサイドバー、状態表示、通知、`hyla` コマンドが使えます。各マシンはそれぞれの hylad を動かすので、ノートパソコンを閉じても Hyla を終了しても、ローカルと同じようにリモートのエージェントは動き続けます。

## クイックスタート

ホストとは、Hyla が入っている任意のマシンです。すでに Hyla アプリを使っている別のコンピュータでも、ディスプレイのないサーバーでもかまいません。

### Hyla アプリが入っているコンピュータ

アプリのほかに何もインストールする必要はありません: アプリ自身の hylad がホストとして働きます。ほかのマシンからの接続方法を選びます:

- **Tailscale 経由。** ホスト側のアプリで **設定 › Hyla ホスト › ほかのマシンからの接続を許可** をオンにします。ほかのマシンで追加するアドレス（`http://studio.tail1234.ts.net:7473` など）が表示されます。[Tailscale](#tailscale) を参照してください。
- **SSH 経由。** そのコンピュータが SSH ログインを受け付けるなら（Mac では **システム設定 › 一般 › 共有 › リモートログイン**）、`ssh` に渡すのと同じアドレスで追加します。Hyla はそこにあるアプリを自分で見つけます。

自分のコンピュータと同じように、ホストのセッションはアプリを閉じている間も動き続けます。

### サーバー

Linux マシン、クラウドの VM など、アプリのないマシンには、サーバー版の Hyla をインストールします。root や管理者権限、ディスプレイ、GTK は不要です。Linux や macOS では:

```sh
curl -fsSL https://github.com/smallnest/hyla/releases/latest/download/install-server.sh | sh
```

Windows では、PowerShell で:

```powershell
irm https://github.com/smallnest/hyla/releases/latest/download/install-server.ps1 | iex
```

### ホストを追加する

自分のコンピュータで **設定 › Hyla ホスト** を開き、ホストのアドレス（SSH なら `me@devbox`、またはホストのアプリに表示されたアドレス）を入力して **追加** を押します。ホストのプロジェクトが、それぞれホスト名付きで、あなたのプロジェクトと一緒にサイドバーに表示されます。

コマンドラインでも同じことができます:

```sh
hyla hosts add devbox me@devbox
hyla -H devbox new -n review -- claude
```

::: tip
追加したホストに Hyla がインストールされていなければ、サイドバーにそう表示され、**Hyla をインストール…** が提案されます。これは SSH でホスト上に上のスクリプトを実行します。
:::

## Hyla がホストに接続する方法

アドレスは、ホストへの接続方法を示します。設定、設定ファイル、`hyla -H` の後で、Hyla は同じアドレスを受け付けます。

| アドレス | 方法 |
| --- | --- |
| `devbox`、`me@devbox`、`me@devbox:2222`、`ssh://me@devbox` | `~/.ssh/config`、キー、エージェントを使った SSH |
| `wsl://Ubuntu`、`wsl://` | この Windows PC の WSL ディストリビューション（`wsl.exe` 経由） |
| `http://devbox:7473` | tailnet アドレス上の hylad のリスナー（[Tailscale](#tailscale) を参照） |
| `https://devbox.tail1234.ts.net` | Tailscale Serve の背後にある hylad |
| `tailcat://tc…` | ペアコード。リレー経由で接続し、Tailscale は不要です（[Tailcat](#tailcat) を参照） |

Hyla はホストごとに 1 本の接続を開き、すべてをそこに載せます: サイドバーの状態、表示しているすべてのペイン、CLI のコマンド。接続は圧縮され、ハートビートが切れた接続を数秒で検知します。ノートパソコンのスリープなどで接続が切れると、ホストのセッションは薄く表示されたままサイドバーに残り、Hyla は自動で再接続します。再試行の間隔は最大 1 分まで延びていきます。

### SSH

SSH では、Hyla はホスト上で `hyla __bridge` を実行します。これは、hylad が動いていなければ起動し、接続をそこに渡します。ホストには Hyla 自体（アプリかサーバー版）のほかに何もセットアップする必要はなく、ネットワークで待ち受けるものもありません。

アプリには答える人がいないので、Hyla は SSH で何かを尋ねることはありません:

- **パスフレーズ付きのキー** には SSH エージェントが必要です。Hyla は、ターミナルの `ssh` と同じく、シェルが `SSH_AUTH_SOCK` に設定したエージェント（1Password のものなど）を使います。
- **初めて接続するホスト** は、先にそのキーを信頼する必要があります。ターミナルで一度 `ssh me@devbox` を実行してください。
- **パスワードログイン** には対応していません。キーを使ってください。

Hyla は、ホスト上の `hyla` を `~/.local/bin`（Windows では `%LOCALAPPDATA%\Programs\hyla-server`）、デスクトップアプリとそのコマンドラインツール、`PATH` から探します。ほかの場所にある場合は、アドレスで指定します: `me@devbox?hyla=/opt/hyla/hyla`、Windows なら `me@pc?hyla=C:/hyla/hyla.exe`。

### Windows ホスト

Hyla は SSH で Windows マシンに接続するので、先に OpenSSH Server をオンにしてください（管理者として **設定 › システム › オプション機能**）。Hyla は、サーバーのデフォルトのシェルである cmd と、PowerShell のどちらでも動きます。どちらなのかは最初の接続時に調べるので、その接続には少し時間がかかります。

インストールスクリプトは、hylad をタスクスケジューラのあなたのタスクとして登録し、マシンにログオンしたときにあなたのセッションで起動します。誰もログオンしていない間は、Hyla が接続したときに hylad が起動し、接続が終わった後も動き続けます。そのように起動した hylad は、キーを使った SSH のプログラムと同じく Windows のパスワードなしで動くので、そのセッションのプログラムはネットワーク共有や、Windows が保存している資格情報にアクセスできません。アカウントのすべての権限で動かすには、一度マシンにログオンするか、ログオン後に hylad を再起動してください。

### WSL

Windows では、`wsl://Ubuntu` で、SSH と同じようにその WSL ディストリビューションにインストールされた Hyla に接続します。`wsl://` はデフォルトのディストリビューションです。そこに Hyla がインストールされていなければ、SSH のときと同じくインストールを提案します。

WSL は、Windows から起動した最後のプログラムが終わってしばらくすると、ディストリビューションを停止することがあり、hylad も一緒に止まります。エージェントを動かし続けるには、たとえば [systemd を有効にして](https://learn.microsoft.com/windows/wsl/systemd)その中で `hyla daemon install-service` を実行し、ディストリビューションを起動したままにしてください。

### Tailscale

hylad は tailnet で待ち受けることもでき、その場合 SSH はまったく不要です。誰が接続しているかは Tailscale が hylad に伝え、デフォルトではマシンを所有する Tailscale ユーザーだけが入れます。アプリのあるホストでは、**設定 › Hyla ホスト › ほかのマシンからの接続を許可** をオンにすると、ほかのマシンで追加するアドレスが表示されます。サーバーの場合や手で設定する場合は、ホストの設定に次を追加します:

```ini
# ホスト上の ~/.config/hyla/config
listen = tailnet://:7473
```

その後、ホストを `http://devbox:7473` として追加します。接続はプレーンな HTTP ですが、tailnet のデバイス間では WireGuard が暗号化します。

代わりに Tailscale の証明書を使って HTTPS で提供するには、hylad にソケットで待ち受けさせ、Tailscale Serve をそこに向けます:

```ini
listen = tailnet-serve://
```

```sh
tailscale serve --bg --https=443 unix:$HOME/.config/hyla/serve.sock
```

その後、ホストを `https://devbox.tail1234.ts.net` として追加します。ソケットは Hyla のデータフォルダにある `serve.sock` です: Linux では `~/.config/hyla`、macOS では `~/Library/Application Support/hyla`。

所有者以外の接続を許可するには、`listen-allow` に列挙します: tailnet のログイン、タグ付きデバイスなら `tag:ci`、tailnet 上の誰でもなら `*`。タグ付きのマシンには所有者がいないので、`listen-allow` だけが接続を許可します。Tailscale Serve はタグ付きデバイスが誰なのかを hylad に伝えないので、それらは `tailnet://` リスナーに接続します。

```ini
listen-allow = alice@example.com
listen-allow = tag:ci
```

hylad は `listen` と `listen-allow` の変更に追従し、オフにしたリスナーはそれが受け付けた接続を切ります。hylad の動作中に追加した `tailnet-serve://` リスナーは、`hyla daemon restart` まで待機します。hylad が待ち受けるのは設定で求められたときだけで、Tailscale 上だけです。Web ブラウザからのリクエストは拒否するので、訪れた Web ページから接続されることはありません。インターネットからの Funnel のリクエストは決して入れません。マシンの起動とともに待ち受け続けるには、サービスとして実行してください（下記）。

### Tailcat

Tailcat は Tailscale の代わりに、ペアコードでホストに接続します。どちらのマシンにも Tailscale のアカウントも Tailscale 本体も要りません。[Tailcat](https://github.com/tailscale/tailcat) を使います。これは Tailscale の部品から作られたライブラリで、2 台のマシンの間に WireGuard のトンネルを作ります。まず公開 DERP リレーを通して互いを見つけ、見つかった後は、ネットワークが許せば直接接続します。

ペアコードがホストのアドレスです。ホストの公開鍵、事前共有鍵、リレーのリージョンを含む長い `tc…` の文字列です。**パスワードとして扱ってください: 持っている人は誰でもホストに接続できます。**

**Settings › Hosts › Tailcat** に、Tailcat の設定がすべて 1 つのグループに入っています。上部のスイッチ **Tailcat でほかのホストに接続** でまとめてオンになります。オンのとき、グループは 2 つの部分に分かれます:

- **Add a Host**: このマシンが接続するホストを追加します。相手のマシンの Tailcat グループ、またはそのマシンで `hyla hosts tailcat code` を実行して、ペアコードをコピーします。**リモート Tailcat のポート** は追加するホストの tailcat リスナーのポートです。別のものを指定しなければ 7473 です。
- **Tailcat サービスを提供**: このマシンをホストにします。Hyla はそのペアコードをコピーのボタン付きで表示します。**このコンピュータの Tailcat リスナーポート** はここで hylad が待ち受けるポートです。**Change the pair code** は新しいペアコードにします。

ペアコードにリスナーのポートは入っていません。ほかのマシンの **リモート Tailcat のポート** には、ホストの **このコンピュータの Tailcat リスナーポート** を設定してください。

**Relay** は、すべてのマシンがリレーを見つける DERP マップです。両方の部分で使います。

クライアントには、このバージョン以降の Hyla が必要です。

同じ設定はコマンドラインでもできます:

```sh
# ホストで: 先に Tailcat をオンにし、待ち受けます。
# 設定に tailcat = true を先に書きます。
hyla hosts tailcat enable  # または hyla hosts tailcat enable 7400
hyla hosts tailcat code    # ペアコード（秘密）
hyla hosts tailcat rotate  # 新しいペアコード。古いコードは使えなくなります

# もう一方のマシンで:
hyla hosts add box tailcat://tc…
```

ペアコードは hylad を再起動しても変わりません。hylad は起動時にログにも記録します:

```sh
grep 'listening on tailcat' ~/.config/hyla/hylad.log
```

ログは macOS では `~/Library/Application Support/hyla`、Windows では `%LOCALAPPDATA%\hyla` にあります。

**スイッチ。** Tailcat は初期状態ではオフです。オフのとき、アプリは Tailcat のホストを一覧に出さず、接続もしません。hylad は `tailcat://` のリスナーを開始しません。リレーを信頼しない場合は Tailcat をオンにしないでください。オフのままなら、Hyla は Tailcat のために何も起動しません。

**リレー。** 既定では、Tailscale が `https://tailcat.dev/derpmap.json` で提供する公開リレーを使います。Tailscale はその速度を制限し、常に使えることを保証していません。2 台のマシンがネットワーク上で直接届き合える場合、セッションのデータはリレーを通りません。リレーは互いを見つけるための情報だけを運びます。自分のリレー（Tailscale の [derper](https://github.com/tailscale/tailscale/tree/main/cmd/derper) など）を使うには、`tailcat-relay` に DERP マップの URL を設定します。アプリの **Relay** でも同じです。ホストと相手側の両方で同じマップを設定します。ペアコードにはリレーの番号だけが入り、それぞれの側が自分のマップでそれを見つけます。

**ペアコードの変更。** アプリの **Change the pair code** または `hyla hosts tailcat rotate` で新しい鍵を作ります。hylad は新しい鍵でリスナーを開始し直し、古いコードでは接続できなくなります。ほかのマシンでこのコンピュータを追加し直してください。マシンからコードを削除するには、そのデータフォルダーの鍵ファイル `tailcat.json` を削除します。

**スイッチでは変えられないこと。** クライアントはリレーとホストを区別できません。リレーを管理し、ペアコードも持っているマシンは、ホストになりすませます。Tailscale の公開リレーなら、これには Tailscale のサーバーへの攻撃が必要です。自分のリレーなら、それを動かしている人ができます。

**鍵。** hylad は Tailcat の鍵を Hyla のデータフォルダーの `tailcat.json` に保存し、あなたのユーザーだけが読めます。このファイルが変わらなければ、ペアコードは再起動後も同じです。削除して hylad を再起動すると新しい鍵になり、**Change the pair code** と同じ結果になります。古いペアコードを持つマシンはホストに接続できなくなります。

## hylad をサービスとして実行する

アプリのあるホストでは、アプリを開いたときか、Hyla が SSH で接続したときに hylad が起動します。サーバーでは、hylad を自分のサービスとして実行すると、マシンの起動とともに開始し、誰もログインしていない間もセッションを動かし続けられます。インストールスクリプトがこれを行います。Mac では、サービスは launchd エージェントで、Mac にログインしている間だけ動くので、ログインしたセッションを残しておいてください（ログインしていればスクリプトがインストールします）。Windows では、ログオン時に hylad を起動するタスクスケジューラのタスクです。

```sh
hyla daemon install-service      # systemd ユーザーユニット、macOS では launchd エージェント、Windows ではタスク
hyla daemon status               # 動作の仕方と、待ち受けている場所
hyla daemon uninstall-service
```

Linux では、まず lingering（`loginctl enable-linger`）を有効にします。これにより、ログアウト後もサービスが動き続けます。これがないと、最後の SSH セッションが終わったときにサービスが止まってしまいます（必要に応じて起動した hylad はそれより長く動きます）。そのため `install-service` は lingering なしでは先に進みません。lingering に管理者の許可が必要なシステムでは、管理者に `sudo loginctl enable-linger <you>` を実行してもらうか、`--no-linger` を付けてサービスをインストールしてください。

`hyla daemon serve` は、独自のサービスマネージャ向けに、hylad をフォアグラウンドで実行して標準エラーにログを出力します。アイドルを理由に終了することはありません。`--listen` は設定の `listen` キーの代わりになります。

## ホストで作業する

- **サイドバー。** プロジェクトを、あなたのものを先に、次に各ホストのものを **設定 › Hyla ホスト** の順に一覧します。ホストのプロジェクトには `api` `devbox` のように名前の後にホスト名が付くので、2 台のマシンの同じリポジトリが並んで表示されます。ホスト専用の行が現れるのは、あなたの対応が必要なときだけです: Hyla が接続できないとき、アップデートが必要なとき、インストールされていないとき。セッションのないホストは表示されません。プロジェクトを開くでそこにセッションを開始してください。ホストのプロジェクトを右クリックすると、ホストのメニューが開きます: 再接続、hylad の再起動、Hyla のアップデート、カラー、ホストの設定。
- **カラー。** 各ホストには名前から選ばれたカラーがあります: サイドバーのタグとペインのヘッダーのホスト名にその色が付くので、リモートのペインがひと目でわかります。ホストのメニューの **カラー** か、アドレスの後の `color=`（`host = devbox=me@devbox color=teal`）で別の色を選べます。
- **新規セッション。** <kbd>⌘</kbd> <kbd>T</kbd> と **新規セッション** は、表示中のセッションのホストでセッションを開始します。プロジェクトの **+** は、そのマシンのそのプロジェクトでセッションを開始します。
- **プロジェクトを開く。** ホストを追加していると、<kbd>⌘</kbd> <kbd>O</kbd> はコンピュータのダイアログの代わりに Hyla の中でフォルダを一覧し、表示中のセッションのマシンから始めます。上部の切り替えで別のマシンのフォルダを一覧できます。入力して絞り込むか、`~/code` のようなパスを入力します。<kbd>↩</kbd> でフォルダの中に入り、<kbd>⌘</kbd> <kbd>↩</kbd> か **開く** でプロジェクトとして開きます。
- **パス。** リモートのペインでファイルパスを <kbd>⌘</kbd> クリックすると、下のペインでホストの `$EDITOR` でそのファイルを開きます。フォルダはそこで新しいセッションとして開きます。Hyla が、たまたま同じパスにあるあなたのコンピュータのファイルを開くことはありません。画像のパスに <kbd>⌘</kbd> を押しながらポインタを合わせると、ホストの画像をプレビューします。
- **画像とファイルのペースト。** リモートのペインに画像やファイルをペーストすると、ホスト上の非公開の一時フォルダにコピーされ、そのパスがペーストされます。Claude Code のように画像のパスを読むエージェントも、そのまま動きます。ファイルをリモートのペインにドラッグした場合は、あなたのコンピュータのパスがペーストされます。
- **エージェント。** リモートのペインの中では、`hyla` はそのホストの hylad と通信するので、エージェントのスキルはそのまま動きます。ホストで `hyla skill setup` を実行してください。
- **通知。** ホストの通知とウインドウのタイトルにはホスト名が付くので、リモートのプログラムがローカルのものになりすますことはできません。

### リモート操作

`hyla focus` と `hyla do` を使うと、プログラムがアプリを操作できます。ホストの場合、それは別のマシンのコードがあなたのコンピュータのウインドウを操作することになるので、デフォルトではオフです。**設定 › Hyla ホスト** でホストごとにオンにするか、アドレスの後に `remote-control` を付けます:

```ini
host = devbox=me@devbox remote-control
```

### 設定

外観、キーボード、通知はアプリの設定です。ホストのシェル、`env`、スクロールバック、セッションの復元は、hylad がそこで読み込むので、そのホストの設定から来ます。変更するには、ホストで `hyla config edit` を実行してください。

## バージョンとアップデート

アプリとホストは、異なるバージョンの Hyla を実行できます。ホストがアプリより古いリリースを実行していると、サイドバーのその最初のプロジェクトに **アップデート** が表示されます。これは、アプリのバージョンの Hyla をホストにダウンロードし、そのバージョンとプラットフォームについて Hyla 自身のアップデートの署名に使われるキーで検証してから、そこで hylad を再起動します。再起動するとホストのセッションは履歴とともに元の場所から再開し、そこで実行中のプログラムは終了するので、Hyla は先に確認します。

- Hyla がホストをアップデートするのは、あなたが求めたときだけです。再接続時には行わず、古いバージョンに戻すこともありません。
- ホストがアプリより新しい Hyla を実行しているときは、代わりにアプリをアップデートしてください（**設定 › 一般**）。
- Hyla がアップデートするのは、インストールスクリプトでインストールしたものです。ホストに別の方法で Hyla をインストールした場合は、インストールしたときと同じ方法でアップデートしてください。
- Hyla デスクトップアプリを実行しているホストは、許可すればほかのマシンからアップデートを受けられます: そのコンピュータで **設定 › Hyla ホスト › ここの Hyla のアップデートを許可**（`remote-updates = true`）をオンにします。するとそこのアプリは最新のリリースにアップデートし、再起動して、hylad を再起動します。それまでは、そのコンピュータでアップデートしてください。

コマンドラインから:

```sh
hyla -H devbox version           # この hyla のバージョンと、ホストのバージョン
hyla -H devbox daemon status
hyla -H devbox daemon update     # この hyla のバージョンへ
hyla -H devbox daemon restart
hyla daemon update               # ホスト上で、最新のリリースへ
hyla daemon update 2.1.0         # ホスト上で、指定したバージョンへ（古いものも可）
```

## コマンドライン

コマンドの前の `-H`（または `--host`）は、セッションに対するコマンドをホストの hylad に向けます。ホストの名前、アドレス、またはこのマシンを示す `local` を受け付けます。`$HYLA_HOST` も同じですが、ペインの中では `hyla` はペイン自身のマシンに対して動きます。`hyla config` や `hyla hook` のようなこのマシンだけのコマンドは、`$HYLA_HOST` を無視します。

```sh
hyla hosts                       # 追加したホスト（JSON なら --json）
hyla hosts add build ci@build.lab --remote-control
hyla hosts check build           # 接続して結果を表示。名前かアドレス
hyla hosts install build         # SSH か WSL でそこに Hyla をインストール
hyla hosts remove build
hyla ls --all                    # このマシンとすべてのホストのセッション
hyla -H build ls
hyla -H build prompt review "run the tests and fix them"
hyla clients                     # このマシンの hylad に接続しているもの
```

アプリと CLI は、ひとつのホストのリスト、つまり設定の `host` キーを共有します:

```ini
host = devbox=me@devbox
host = build=ssh://ci@build.lab:2222 remote-control
host = ubuntu=wsl://Ubuntu
```

| 変数 | 働き |
| --- | --- |
| `HYLA_HOST` | `-H` と同じく、コマンドを向けるホスト |
| `HYLA_SSH` | `PATH` にあるものの代わりに Hyla が実行する `ssh` プログラム |
| `HYLA_RELEASES` | インストールスクリプトと `hyla daemon update` 用の、Hyla のリリースのミラー |

## セキュリティ

- **接続は、そのアカウントにできることは何でもできます。** ローカルの接続と同じく、プログラムの起動も含みます。SSH では、SSH がログインさせるあなた自身のアカウントです。Tailscale では、マシンの所有者が許可した人だけです。
- **ソケットはあなた専用です。** hylad のソケットはそのユーザーだけが読める状態で作られ、hylad はほかのユーザーのプロセスからの接続を拒否します。
- **アップデートは署名されています。** サーバー版は、Hyla のリリースのキーで署名されたアーカイブからのみ自分をアップデートします。
- `hyla clients` は、hylad に接続しているものを、その接続方法とともに一覧します: `uid 501 over unix`、`me from 10.0.0.5 over ssh`、`alice@example.com over tailnet`。

## 制限

- サーバー版は、glibc 2.28 以降の Linux、macOS、Windows 10（1809）以降の、x86-64 と ARM64 に対応しています。Hyla アプリのあるマシンにはサーバー版は不要です。
- ファイルをリモートのペインにドラッグすると、あなたのコンピュータのパスがペーストされます。代わりにペーストしてください。
- 1 つのホストには 1 つのアカウントです。複数の人が 1 台のマシンでそれぞれのアカウントに接続するログインサーバーには、今後対応する予定です。
